Catch up to official (fetch `upstream/dev`, **merge** into `main` — rerere records recurring conflict resolutions, build, push `origin/main`, install binary):

```bash
bun run sync-upstream
```

- Dirty tree → commit or stash first; the script refuses to run dirty.
- Merge conflict → fix files, then:

```bash
git add -A && git commit --no-edit
bun run sync-upstream --continue
```

- Git only, skip compile: `bun run sync-upstream --no-rebuild`
- `--continue` requires a clean `main` containing `upstream/dev`; it refuses an uncommitted merge (and any stray rebase state), including linked worktrees. Dependency or build failures stop before pushing.
- After the merge, and again right before the push, the script refuses to continue if upstream brought back a deleted self-upgrade/web path — the `packages/cli/src/commands/handlers/{upgrade,uninstall}.ts` files, their `src/index.ts` loaders and `Spec.make("upgrade"/"uninstall")` specs, the deleted `packages/desktop` tree, or a resurrected updater network endpoint (`opencode.ai/(update/api|v2/install)`, `formulae.brew.sh/api/formula/opencode`; `assertForkInvariants`). Remove them, commit, `--continue`.
- Machine can't reach GitHub directly? Set the proxy repo-locally (lives in `.git/config`, per machine, not in this doc): `git config http.proxy http://127.0.0.1:PORT && git config https.proxy http://127.0.0.1:PORT`

Repo ↔ seat drift audit (read-only, exit 1 on drift; `bootstrap/verify.sh` is the seat-side counterpart):

```bash
bun run check-drift
```

After any source change that should hit the TUI, rebuild if you skipped it:

```bash
cd packages/cli
bun run script/build.ts --single --skip-install --skip-web-ui
oc_stage=$(mktemp ~/.opencode/bin/.opencode-install.XXXXXX)
cp dist/cli-<platform>-<arch>/bin/opencode "$oc_stage" && chmod +x "$oc_stage" && mv "$oc_stage" ~/.opencode/bin/opencode
~/.opencode/bin/opencode --version
```

`--single` builds only the current platform, so exactly one `cli-<platform>-<arch>` dir exists (`darwin-arm64`, `darwin-x64`, `linux-x64`, …) and the glob picks it up.

Replacing the binary while a TUI is running arms a delayed replacement: a running managed service re-reads its registration file every 5 seconds and shuts itself down when a newer client registers over it (`packages/cli/src/services/service-registration.ts`, "managed service registration replaced; shutting down"), and the next launch shows the preflight footer (`packages/cli/src/services/update-preflight.tsx`). Swap the binary when no TUI is running, or expect the next launch to replace the old server. Install via temp file + `mv` (atomic rename): `cp` onto the live path can fail with ETXTBSY.

Credential cleanup (`auth purge` removes stored credentials and every stale copy of their values — auth/env files by value, session/event rows with `secure_delete`; output is counts only, never key values). Targets match an integration id, a name, or a substring of either; an ambiguous or empty target lists candidates and fails; non-interactive runs need `--yes`. Since 2026-10-15 a target may also name a **removed** integration: when nothing in the live catalog matches, the candidate list is completed from the credential store, so the key of a vendor whose config block is gone is still purgeable by id — the catalog alone could not see it, which is the defect the removal exposed:

```bash
opencode auth purge deepseek --yes [--dry-run] [--no-files] [--history] [--compact]
```

In the TUI: `/usage` shows per-session and per-model usage with compaction accounting; `/purge-keys` drives `auth purge` interactively.

## How to keep personal patches

1. All custom work lands as commits on **`main`**, stacked on top of `upstream/dev`.
2. Commit prefix for overlay work: `eric: …` (matches existing history).
3. **Upstream sync is merge-based** (since 2026-09-28): rebases were abandoned in practice — reflog shows merges since Sep 17; a rebase would flatten those conflict resolutions and replay ~45 commits. The script enables `rerere.enabled` so recurring conflicts (e.g. the Zen-provider deletion) auto-resolve after the first manual resolution. Pushes are normal (no force) because merges never rewrite history.
4. `~/.config/opencode/opencode.jsonc` (provider/model) is local-only. `cli.json` is in the repo; deployment is a separate step — `installTuiConfig` in `sync-upstream` reads the repo-root `cli.json` and seeds the seat copy only when it is absent, so the seat keeps its own tuning and `check-drift` reports the file as a seed rather than drift (closed 2026-10-15; the earlier note described a `dotfiles/opencode/cli.json` that does not exist). Launching from `$HOME` does **not** read the repo-root file. Same for `skills/`: it is in the repo, generated by `bun run vendor-skills`, and `sync-upstream` installs it to `~/.config/opencode/skills/`. Same for goal mode: `dotfiles/opencode/{agent/goal.md,AGENTS.goal.md,autonomy.md}` — `sync-upstream` installs them (AGENTS.goal.md + autonomy.md replace in place; `agent/goal.md` is a seed, installed only when absent so per-machine model pinning survives). There is **no** `command/goal.md` anymore (the `/goal` command was removed 2026-10-06 — goal mode owns its objective; see the reminders entry below). The `instructions` entries pointing at `autonomy.md` and `AGENTS.goal.md` are **one-time manual lines** in the local `opencode.jsonc`.

If a merge conflict hits a file you patched, keep the personal behavior unless the owner says otherwise.

Long-lived decisions are recorded as ADRs in `docs/adr/` (format and when-to-write: `skills/domain-modeling/ADR-FORMAT.md`). Current set: source-built binary / no self-upgrade, merge-only upstream sync, exhaustive config-declared providers, Zen removal, vendor support (DeepSeek only since ADR 0009/0010; every other vendor is deleted, so a sync will conflict on deleted provider files — `git rm` them), Zhipu/Z.AI and unused Xiaomi plans removed, the desktop app's removal (this fork is TUI-only), and DeepSeek as the only supported vendor with the operator's non-DeepSeek blocks and credentials removed (ADR 0010).

## Project config trust gate (untrusted repositories)

Opening a repository can execute code at session start with no prompt: `.opencode/plugin/` and `.opencode/plugins/` are imported automatically (discovery walks upward from the session's location directory with no stop boundary — `config/discovery.ts:33-35` — and every `.opencode` found on the way is collected at `:66-69`; the chain is `config/plugin/source.ts:127-133` → `plugin/source-directory.ts:7`, `:21-32` → `plugin/module.ts:120-124`, which imports the module and runs its `effect`/`setup`), a config document's `plugins` array is imported the same way (`config/plugin/source.ts:134-147`), and MCP `command` servers from project config are spawned asynchronously when a Location starts (`config/plugin/mcp.ts:39-56` → `mcp/index.ts:537-559` → `mcp/stdio.ts:84-96`; `disabled: true` opts out). A config `lsp.<name>.command` is the same class of vector: it replaces the server spawn (`fork/lsp/lsp.ts:119-135`) and runs on the first file touch or read warmup. The only veto is the managed policy layer — config `experimental.policies` documents, enforced as `integration.use plugin:<target>` (`plugin/module.ts:52-59`) and through the MCP/skill/provider transforms — which defaults to **allow** when none is configured (`managed-policy.ts:69-77`); the Console organization-statement path has no in-tree producer, and this seat carries no policy.

Escape hatch for untrusted trees: `OPENCODE_CONFIG_PROJECT_DISABLE=1` (alias `OPENCODE_DISABLE_PROJECT_CONFIG`; truthy is `"1"` or case-insensitive `"true"`, and the primary name wins even when falsy — `0` masks the alias — `cli/src/server-process.ts:118-120`) sets `config.project = false` and discovery skips the upward walk entirely. The value is read once when the server process starts, so exporting it later in a client does nothing to an already-running shared server. Trade-offs: it also disables this repo's own `.opencode/` config and upward project instruction discovery (`instruction-discovery.ts:99`), so it is an opt-in for opening foreign repositories, not a wrapper default.

Permission rule order (pinned, not a deny guarantee): `Permission.evaluate` scans with `Array.findLast` (`permission.ts:87-97`) — the **last** matching rule wins, and no match asks. Rulesets merge flat in load order, and documents load managedPolicies → wellknown → global → explicit → direct → project → content → managedSettings (`config.ts:280-287`; ADR 0008), so a project document can re-allow what a global one denied, while a managed settings document (loaded last) overrides both; document-level permissions are appended to every agent and then `agents.<id>.permissions` append after (`config/plugin/agent.ts:84-92`, `:121-124`), so write the deny last to beat a broader allow. Saved approvals land after configured rules, but a configured deny short-circuits before they are consulted (`permission.ts:165-177`): a saved allow elevates an `ask` and never overrides a `deny`. Pinned by `packages/core/test/permission-precedence.test.ts`; a failure there means a deliberate decision about the ordering is due — do not "fix" `findLast` without an upstream design change.

Platform note: measurement (`ps`, TSV) is cross-platform. Stack capture uses
`sample(1)` on macOS and `eu-stack -p` (elfutils) on Linux, with fallbacks to
`gdb -batch -ex 'thread apply all bt'` and finally to the bare ps/wchan thread
table (states still classified, no frames). Linux attach needs ptrace access:
fine when `kernel.yama.ptrace_scope=0`; with scope=1 only the process parent
may attach. The Linux thread table also names Bun's threads (HeapHelper,
JITWorker, Bun Pool N), which sample(1) does not.

Rules when using them:

- Every opencode instance on the box shares one
  `~/.local/share/opencode/log/opencode.log`, so cpu-probe's idle gate is
  **global**, not per pid. Run it when only the suspect instance is up, or pass
  `--exclude` for the busy one.
- Stack capture **suspends the target's threads** (sample(1) on macOS,
  eu-stack/gdb attach on Linux). Never aim it at a session doing real work
  without asking the owner first. `ps` and `lsof` are read-only and always safe.
- `pgrep(1)` returns nothing under some sandboxed shells; both scripts discover
  pids through `ps -axo pid=,comm=` instead.

## Mouse garbage in shell after hard kill (fixed via wrapper)

Two distinct signatures — do not confuse them:

1. **Continuous** garbage on every click/move after exit = mouse modes left ON.
   Only a hard death does this (kill -9, crash, or killing a frozen instance —
   see the idle-spin issue above); clean exits (`/exit` idle or mid-stream,
   SIGTERM, SIGHUP) all emit the full disable sequences — verified by pty byte
   capture and by tmux `mouse_any_flag`/`mouse_sgr_flag` before/after. Neither
   VTE/Ptyxis nor tmux resets the modes when the child dies.
2. **One-shot** tail like `35;54;13M` right after the prompt, even on a clean
   `/exit` of a fresh session = queued-input residue, not a mode leak. During
   the exit window (renderer detached stdin, terminal has not yet applied the
   disable sequences) a mouse move report lands in the pty input queue; bash
   readline later echoes it and it pollutes the next typed command. Reproduced
   deterministically: `tmux send-keys -l $'\e[<35;54;13M'` at the moment of
   `/exit` shows the tail after the prompt; with the fix it does not.

Fix (both): the `opencode()` wrapper in `~/.bashrc` (per machine, outside git) —

- `_oc_tty_reset`: idempotent disable sequences (mouse `?1003l/?1002l/?1000l/?1006l`,
  paste `?2004l`, `?2031l`, `>4;0m`, cursor visible), printed **before launch**
  (clears stale leaks from an earlier hard death in the same tab) and **after
  the binary returns** (covers hard death of this run). `[[ -t 1 ]]`-guarded so
  `opencode run` pipes stay clean; exit code preserved.
  **Never put `?1049l` in the wrapper**: both VTE and tmux restore the cursor
  from the stale `?1049h` save slot when they receive `?1049l` while already on
  the main screen, which draws the next prompt on an old line above and shuffles
  the visible line order (reproduced in tmux 2026-09-18). VTE leaves the alt
  screen by itself when the child dies; the rare tmux stuck-in-alt case after a
  hard kill is repaired manually with `printf '\e[?1049l'` or `reset`.
- `_oc_tty_flush_input`: `tcflush(TCIFLUSH)` on `/dev/tty` via python3 after
  exit — drops queued mouse reports (signature 2). Millisecond in-flight
  reports can still slip through; that residue is cosmetic.

Tabs whose bash predates the fix still run the old function: `source ~/.bashrc`
or open a new tab. Repair an already-broken terminal with `reset` or:
`printf '\e[?1003l\e[?1002l\e[?1000l\e[?1006l\e[?2004l\e[?1049l\e[?25h'`

Note: a pre-TUI startup death (crash/Ctrl+C before the renderer is created) never
enables mouse modes and needs no cleanup; the leak always comes from a TUI that
got past renderer init and then died hard.

Do not "fix" this by disabling mouse in the TUI — in-app click/scroll is intentional.

## TreeSitter warning flood on exit (fixed via opentui patch)

## 2026-10-15: shell and tool output are sanitized before rendering

`strip-ansi` removes *well-formed* escape sequences only. A byte-level probe against the real
`DialogShellOutput` path (now `packages/tui/test/component/shell-output-sanitization.test.tsx`) fed 35
payloads through it and 20 of them put a control byte into the rendered frame:

| Payload | Why `strip-ansi` misses it | Terminal effect |
| --- | --- | --- |
| `\x1b\x00[31m` | the NUL sits inside the introducer, so the ANSI regex cannot match | the sequence survives *and* the gap keeps it live: clear screen, alt screen, OSC 52 clipboard write, OSC 8 link, title rewrite |

| `\x9b31m`, `\x9d52;c;…\x9c` | C1 8-bit forms, not matched by the C0-based patterns | CSI/OSC in 8-bit form |
| `\x1bPq…\x1b\\`, `\x1b\\` | DCS/ST pairs | device-control stream |
| model-authored command line | echoed raw in the shell tab and the dialog header | same as above, but the model chooses the bytes |

### What a restart does (measured 2026-10-16, including the 01:08 replacement that already ran)

The managed service was already replaced once today — a TUI built 1612 replaced the 1516 service
(`reason=version-mismatch`); the owner's two older TUIs lost the event stream for ~1.5 s, reconnected
without replacing anything, and an in-flight session resumed and kept making model requests. The path,
verified against the code and that log:

- SIGTERM interrupts the main fiber; scope finalizers run inside a ~5 s budget
  (`packages/client/src/effect/service.ts:182-197`, 100 × 50 ms poll), then the client SIGKILLs. "Graceful"
  means "fits the budget", not "always clean".
- The write-ahead execution claim survives (nothing commits on shutdown), and boot's sweep resumes every
  claimed top-level session with a synthetic "The server restarted… continue" message — at most 10
  attempts (`packages/core/src/session/execution/restart.ts:33`), then the session fails with
  `RESUME_EXHAUSTED`. Any interruption that recorded no reason is classified `shutdown`, so an eviction
  preserves the claim too.
- The in-flight tool call is durably rewritten as `aborted` ("Tool execution interrupted"); the model
  decides whether to redo it, and external side effects already performed are never rolled back.
- **Foreground subagents are not resumed** (`releaseChildClaims` runs at boot, `restart.ts:205`); the
  parent must re-dispatch them. Background subagent jobs resume from the DB-backed KV, and running
  background shells are reported cancelled.
- Durable history, queued prompts, the session's agent, and the goal file survive. Lost: the last
  unflushed stream deltas, pending permission prompts, and any tool result the process died before
  recording.
- `opencode service restart` shuts the persistent PTY daemon down first, so TUI terminal panes die. A
  version-mismatch *replacement* (launching a newer TUI) hands the daemon over instead.
- A launch from an **older** binary replaces the service with that older binary — a downgrade plus another
  restart. Install the new binary first, then restart from the installed path.
- Never start a second `serve --service --port N` against the same database: the incumbent check probes
  the new service's own port, so it misses the registered one, sweeps immediately, and double-drains for
  ~5–7 s until the old service self-evicts.

## Agent rules for this fork

- Default branch for diffs and PRs against **this** repo is `main`, not `dev`.
- Do not open PRs to `anomalyco/opencode` unless the owner explicitly asks.
- Do not add a second long-lived branch “to keep things clean”.
- After overlay code changes, either run `bun run sync-upstream --continue` (if a merge just finished) or rebuild the binary so `~/.opencode/bin/opencode` matches HEAD.

The unit job now tees its output into `script/affected-guard.ts`, which fails that shape whenever a changed workspace declares a `test` script; when adding a new test-bearing workspace, keep its `test` script declared so the guard can see it.

## 2026-10-16: security audit — is the vendor surface gone, and can a request be routed elsewhere?

Owner question: verify that model support other than DeepSeek (especially the vendor's own free tier) is
removed from the source; assume the tree is untrusted; attack the assumption that a request cannot be
silently routed to a host the operator did not configure.

### Method

Seven Round-1 axes (provider catalog, silent egress, vendor free tier, transport integrity, extension
execution, fork-overlay divergence, built artifact), then five Round-2 attackers whose only assignment was
to kill a finding, by experiment through the installed binary in isolated `HOME`/XDG/DB roots. Reports:
`/tmp/opencode/sec-s{1..7}/report.md`, `/tmp/opencode/attack-sec-{1..5}/report.md`. Every high-severity
verdict below was re-derived here rather than relayed: the binary marker counts, the live socket table, the
service environment key names, the credential table, the CI state, the redirect test, the well-known
substitution test, the registry loader paths, and the tool/MCP registration code.

### The answer

- **The vendor gateway is absent from the product and the artifact.** `zen/v1`, `opencode.ai/zen`,
  `api.opencode.ai`, `opencode.ai/inference`, `OPENCODE_API_KEY`, `big-pickle`, `device/code`,
  `supports_org_scope` count 0 in the installed binary and in both running `/proc/<pid>/exe` images. What
  remains under `opencode.ai` is documentation links, `$schema` metadata, the `webfetch` User-Agent, the
  MCP CIMD `client_id`, and the catalog source below.
- **The seat talks to exactly one host.** Every external socket held by the opencode process tree points at
  `58.251.127.101:443` (= `api.deepseek.com`); the rest is loopback. The live credential table has exactly
  one row (`integration_id = deepseek`), the Console account stores are empty, and no KV key mentions a
  provider, credential, or well-known source.
- **The registry is DeepSeek-only and now pinned to DeepSeek's own endpoint and transports.** Before the
  fix the id allowlist was the only filter, so a poisoned catalog row chose the endpoint (`api`, provider
  and model level) and the npm package imported to speak to it.
- **The vendor catalog host is one opt-in away, and this seat opts out.** `https://models.opencode.ai` is
  the default registry source (`src/models-dev.ts`), gated by `OPENCODE_ENABLE_MODELS_FETCH=1`
  (`cli/src/server-process.ts`). The seat's launcher and the running service carry
  `OPENCODE_DISABLE_MODELS_FETCH`, so the fetch never happens here.
- **CI carries no vendor action that can run.** Exactly `check.yml` and `test.yml` are active, 27 workflows
  are `disabled_manually`, and the fork has **no repository secrets or variables**; only `check` and `test`
  have ever run.
- **No reachable path in the shipped runtime sends anything to a vendor host** (Round-2 verdict, re-derived).
  The outbound surfaces that are *not* the configured provider are the tree-sitter parser download, the
  `references` git fetch, and the LSP download — all three below.

### Killed or reduced by attack

- **The tree-sitter registry is upstream-inherited**, not fork-controlled: `anomalyco` is the upstream
  vendor org, and the fork's only delta is the HTML injections URL named above.

### Residuals registered, not fixed

- The first eight rows are the fork's project-trust boundary: opening an untrusted tree is equivalent to
  running its code. The only switch is `OPENCODE_CONFIG_PROJECT_DISABLE=1`, it is off here, and it is
  server-scoped — a client-side export does nothing when a healthy service is reused, so the durable form
  is `opencode service set env OPENCODE_CONFIG_PROJECT_DISABLE 1` plus a restart.
- The redirect header forwarding lives in Effect's `FetchHttpClient`; `redirect: "manual"` cannot be set
  globally because the LSP and ripgrep downloads rely on cross-origin redirects.
- The well-known `{env:}` fallback and the `${ENV_VAR}` interpolation in a config `baseURL` are upstream's
  variable substitution; narrowing them changes config semantics for every document. For credentials the
  latter is subsumed by the first row (a project that can set `baseURL` already receives the key).
- The tree-sitter downloader has no gate upstream; pre-bundling the 34 parser assets is a build change, and
  the cache is already populated.
- The LSP downloader (fork-owned code, no integrity check) is switched off on this seat with
  `OPENCODE_DISABLE_LSP_DOWNLOAD=1`; a config-declared `command` is not covered by that switch.

### Recommended, awaiting the owner

- Drop the flat `x-opencode-*` identity headers from `model-request.ts` (keep upstream's affinity pair and
  the User-Agent): they exist for the vendor gateway this fork removed, and a privacy-motivated removal
  needs an ADR note because the hunk is upstream's.
- Pre-bundle the tree-sitter assets at build time to close the last ungated egress.
- Consider making the project-config trust gate the default for trees outside the operator's own
  directories; it is the single switch behind the first eight rows.
