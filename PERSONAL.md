
`--single` builds only the current platform, so exactly one `cli-<platform>-<arch>` dir exists (`darwin-arm64`, `darwin-x64`, `linux-x64`, …) and the glob picks it up.

Replacing the binary while a TUI is running arms a delayed replacement: a running managed service re-reads its registration file every 5 seconds and shuts itself down when a newer client registers over it (`packages/cli/src/services/service-registration.ts`, "managed service registration replaced; shutting down"), and the next launch shows the preflight footer (`packages/cli/src/services/update-preflight.tsx`). Swap the binary when no TUI is running, or expect the next launch to replace the old server. Install via temp file + `mv` (atomic rename): `cp` onto the live path can fail with ETXTBSY.

## How to keep personal patches

1. All custom work lands as commits on **`main`**, stacked on top of `upstream/dev`.
2. Commit prefix for overlay work: `eric: …` (matches existing history).
3. **Upstream sync is merge-based** (since 2026-09-28): rebases were abandoned in practice — reflog shows merges since Sep 17; a rebase would flatten those conflict resolutions and replay ~45 commits. The script enables `rerere.enabled` so recurring conflicts (e.g. the Zen-provider deletion) auto-resolve after the first manual resolution. Pushes are normal (no force) because merges never rewrite history.
4. `~/.config/opencode/opencode.jsonc` (provider/model) is local-only. `cli.json` is in the repo; deployment is a separate step — `installTuiConfig` in `sync-upstream` installs `dotfiles/opencode/cli.json` when that copy exists and otherwise falls back to the repo-root `tui.json`, so the root policy file is not deployed today (open item, 2026-10-14). Launching from `$HOME` does **not** read the repo-root file. Same for `skills/`: it is in the repo, generated by `bun run vendor-skills`, and `sync-upstream` installs it to `~/.config/opencode/skills/`. Same for goal mode: `dotfiles/opencode/{agent/goal.md,AGENTS.goal.md,autonomy.md}` — `sync-upstream` installs them (AGENTS.goal.md + autonomy.md replace in place; `agent/goal.md` is a seed, installed only when absent so per-machine model pinning survives). The `instructions` entries pointing at `autonomy.md` and `AGENTS.goal.md` are **one-time manual lines** in the local `opencode.jsonc`.

If a merge conflict hits a file you patched, keep the personal behavior unless the owner says otherwise.

- Kill-guard flag classification (both `bootstrap/agent-hooks/block-unsafe-kill.sh` and `bootstrap/plugin/block-unsafe-kill.ts`, keep byte-identical to the deployed `~/.config` copies): a **quoted or escaped** flag is still a flag once the shell is done (`pkill "-f" vite`, `pkill \-f`, `pkill $'-f'`, `pkill \"-f\"` reached getopt blind before), and short flags bundle (`bash -ec '…'`, `perl -ne '…'` pass the payload to the interpreter just like `-c`/`-e`). Quoted spans are unmasked **only** when the whole span is a plain option NAME (any `-`-led run of `[A-Za-z0-9._+-]` except `-` and `--`; the TS regex is `^-[A-Za-z0-9._+-]+$`, identical charset on both sides); anything else would leak `|;&$\`` into the statement scanner as a phantom `pkill -f`(a first cut used`^-\S+$` and turned `echo "-;pkill" "-f"` into a denial). The charset is wider than what getopt accepts (`-+f` errors out in pkill) — fail-safe on purpose: `pkill "-+f"` blocks in both implementations, pinned by the battery. A cluster letter anywhere counts as the payload flag — when it is not last, getopt gives it the rest of the cluster and the next word is `$0`, but modelling that per-interpreter is getopt simulation, so `bash -ce` / `python -cm` are **known conservative blocks**; `n` excludes the `c` rule because it is no-exec syntax checking in every CODE_SHELLS member (`bash -nc '…'` runs nothing). `has_flag`/`hasFlag` normalize `\`, `$`and one layer of matching quotes before classifying.`guard_rewrite.py`(heredoc in`bootstrap/install.sh`) now matches `verify.sh`'s ref extractor: a bare name mention and an embedded sibling name (`myblock-unsafe-kill.sh`) are data, not paths — it used to rewrite `git commit -m "fix block-unsafe-kill.sh docs"`. Known gaps, deliberately open: a quoted `<<`opens a false heredoc that masks following live lines;`pkill -"f"`splits into`-`and`f` and is not reassembled; long-tail executors (`runuser`, `su -c`, `find -exec`, `awk BEGIN{system}`) run the payload without a recognizable flag. The guard is a pattern matcher, not a shell parser.

## Project config trust gate (untrusted repositories)

Opening a repository can execute code at session start with no prompt: `.opencode/plugin/` and `.opencode/plugins/` are imported automatically (discovery walks upward from the session's location directory with no stop boundary — `config/discovery.ts:33-35` — and every `.opencode` found on the way is collected at `:66-69`; the chain is `config/plugin/source.ts:127-133` → `plugin/source-directory.ts:7`, `:21-32` → `plugin/module.ts:120-124`, which imports the module and runs its `effect`/`setup`), a config document's `plugins` array is imported the same way (`config/plugin/source.ts:134-147`), and MCP `command` servers from project config are spawned asynchronously when a Location starts (`config/plugin/mcp.ts:39-56` → `mcp/index.ts:537-559` → `mcp/stdio.ts:84-96`; `disabled: true` opts out). A config `lsp.<name>.command` is the same class of vector: it replaces the server spawn (`fork/lsp/lsp.ts:119-135`) and runs on the first file touch or read warmup. The only veto is the managed policy layer — config `experimental.policies` documents, enforced as `integration.use plugin:<target>` (`plugin/module.ts:52-59`) and through the MCP/skill/provider transforms — which defaults to **allow** when none is configured (`managed-policy.ts:69-77`); the Console organization-statement path has no in-tree producer, and this seat carries no policy.

Escape hatch for untrusted trees: `OPENCODE_CONFIG_PROJECT_DISABLE=1` (alias `OPENCODE_DISABLE_PROJECT_CONFIG`; truthy is `"1"` or case-insensitive `"true"`, and the primary name wins even when falsy — `0` masks the alias — `cli/src/server-process.ts:118-120`) sets `config.project = false` and discovery skips the upward walk entirely. The value is read once when the server process starts, so exporting it later in a client does nothing to an already-running shared server. Trade-offs: it also disables this repo's own `.opencode/` config and upward project instruction discovery (`instruction-discovery.ts:99`), so it is an opt-in for opening foreign repositories, not a wrapper default.

Permission rule order (pinned, not a deny guarantee): `Permission.evaluate` scans with `Array.findLast` (`permission.ts:87-97`) — the **last** matching rule wins, and no match asks. Rulesets merge flat in load order, and documents load wellknown → global → explicit → direct → project → content (`config.ts:230-237`), so a project document can re-allow what a global one denied; document-level permissions are appended to every agent and then `agents.<id>.permissions` append after (`config/plugin/agent.ts:84-92`, `:121-124`), so write the deny last to beat a broader allow. Saved approvals land after configured rules, but a configured deny short-circuits before they are consulted (`permission.ts:165-177`): a saved allow elevates an `ask` and never overrides a `deny`. Pinned by `packages/core/test/permission-precedence.test.ts`; a failure there means a deliberate decision about the ordering is due — do not "fix" `findLast` without an upstream design change.

is `Sep 4 15:08`, the commit is `15:10:35`; the tell is that the
`@opencode-ai/plugin@0.0.0-main-…` install WARN stops appearing from the first
launch after that rebuild. So 2026-09-10 is a recurrence _after_ the fix.

Ruled out:

- **File watcher.** `OPENCODE_EXPERIMENTAL_FILEWATCHER` defaults to `false`,

  ever happened. `watcher.ignore` in config is therefore a **no-op** in this
  setup. Do not chase idle CPU through watcher ignores, and do not "fix" it by
  requiring a `cd` into a project.
- **Memory / OOM.** Free at the time, no crash report.

Signal worth chasing: `sample(1)` keeps showing a thread parked in opentui's
stdout path — `renderer-output.StdoutOutput.write` → `fs.File.Writer.drain` →
`writev`/`pwrite` against `/dev/ttysNNN`, nested two levels deep, plus a large
`syscall_thread_switch` count in the top-of-stack histogram. The Sep 4 patch
only floored the rerender _scheduler_ (`Math.max(1 → 16)` in `@opentui/core`);
nothing touches the drain path. A terminal tab that stops draining its pty
would make that loop retry forever.

Not yet evidence: a capture taken while the instance was genuinely idle. The
2026-09-10 capture was taken against a live streaming session, so its CPU is
partly legitimate render load.

### Instrumentation

```bash
bun run cpu-probe                       # sampler, auto-captures on idle spin
bun run cpu-probe -- --exclude <pid>    # measure a pid but never sample it
bun run cpu-probe -- --no-capture      # TSV only
bun run freeze-capture                  # one-shot snapshot of a frozen TUI
bun run freeze-capture -- --pid <n> --seconds 10
```

Output goes to `logs/` (gitignored): `logs/cpu-probe/probe-YYYYMMDD.tsv`,
`logs/cpu-probe/spin-*.txt`, `logs/freeze/<stamp>/SUMMARY.txt`.

Platform note: measurement (`ps`, TSV) is cross-platform. Stack capture uses
`sample(1)` on macOS and `eu-stack -p` (elfutils) on Linux, with fallbacks to
`gdb -batch -ex 'thread apply all bt'` and finally to the bare ps/wchan thread
table (states still classified, no frames). Linux attach needs ptrace access:
fine when `kernel.yama.ptrace_scope=0`; with scope=1 only the process parent
may attach. The Linux thread table also names Bun's threads (HeapHelper,
JITWorker, Bun Pool N), which sample(1) does not.

Rules when using them:

- Every opencode instance on the box shares one
  `~/.local/share/opencode/log/opencode.log`, so cpu-probe's idle gate is
  **global**, not per pid. Run it when only the suspect instance is up, or pass
  `--exclude` for the busy one.
- Stack capture **suspends the target's threads** (sample(1) on macOS,
  eu-stack/gdb attach on Linux). Never aim it at a session doing real work
  without asking the owner first. `ps` and `lsof` are read-only and always safe.
- `pgrep(1)` returns nothing under some sandboxed shells; both scripts discover
  pids through `ps -axo pid=,comm=` instead.

## Mouse garbage in shell after hard kill (fixed via wrapper)

Two distinct signatures — do not confuse them:

1. **Continuous** garbage on every click/move after exit = mouse modes left ON.
   Only a hard death does this (kill -9, crash, or killing a frozen instance —
   see the idle-spin issue above); clean exits (`/exit` idle or mid-stream,
   SIGTERM, SIGHUP) all emit the full disable sequences — verified by pty byte
   capture and by tmux `mouse_any_flag`/`mouse_sgr_flag` before/after. Neither
   VTE/Ptyxis nor tmux resets the modes when the child dies.
2. **One-shot** tail like `35;54;13M` right after the prompt, even on a clean
   `/exit` of a fresh session = queued-input residue, not a mode leak. During
   the exit window (renderer detached stdin, terminal has not yet applied the
   disable sequences) a mouse move report lands in the pty input queue; bash
   readline later echoes it and it pollutes the next typed command. Reproduced
   deterministically: `tmux send-keys -l $'\e[<35;54;13M'` at the moment of
   `/exit` shows the tail after the prompt; with the fix it does not.

Fix (both): the `opencode()` wrapper in `~/.bashrc` (per machine, outside git) —

- `_oc_tty_reset`: idempotent disable sequences (mouse `?1003l/?1002l/?1000l/?1006l`,
  paste `?2004l`, `?2031l`, `>4;0m`, cursor visible), printed **before launch**
  (clears stale leaks from an earlier hard death in the same tab) and **after
  the binary returns** (covers hard death of this run). `[[ -t 1 ]]`-guarded so
  `opencode run` pipes stay clean; exit code preserved.
  **Never put `?1049l` in the wrapper**: both VTE and tmux restore the cursor
  from the stale `?1049h` save slot when they receive `?1049l` while already on
  the main screen, which draws the next prompt on an old line above and shuffles
  the visible line order (reproduced in tmux 2026-09-18). VTE leaves the alt
  screen by itself when the child dies; the rare tmux stuck-in-alt case after a
  hard kill is repaired manually with `printf '\e[?1049l'` or `reset`.
- `_oc_tty_flush_input`: `tcflush(TCIFLUSH)` on `/dev/tty` via python3 after
  exit — drops queued mouse reports (signature 2). Millisecond in-flight
  reports can still slip through; that residue is cosmetic.

Tabs whose bash predates the fix still run the old function: `source ~/.bashrc`
or open a new tab. Repair an already-broken terminal with `reset` or:
`printf '\e[?1003l\e[?1002l\e[?1000l\e[?1006l\e[?2004l\e[?1049l\e[?25h'`

Note: a pre-TUI startup death (crash/Ctrl+C before the renderer is created) never
enables mouse modes and needs no cleanup; the leak always comes from a TUI that
got past renderer init and then died hard.

Do not "fix" this by disabling mouse in the TUI — in-app click/scroll is intentional.

## SIGKILL deaths from hermes cgroup_cleanup (fixed via guard)

Symptom (2026-09-19, three times: 16:14 / 16:36 / 16:47, all on binary

tool shell it's the terminal scope (`ptyxis-spawn-….scope`) containing the

call to the millisecond. `timeout 30` was useless — `timeout` died with the
rest of the scope.

`cgroup_cleanup` (both `~/.config/agent-hooks/block-unsafe-kill.sh` and
`plugin/block-unsafe-kill.ts`; read-only and git-commit segments exempt).
Documented in the global rules (`~/.config/opencode/AGENTS.md`). The root-cause
fix belongs in hermes — `reap_cgroup()` should refuse to run outside the
unit's cgroup — handed to the hermes session.

Same day, different cause, undetermined: the 14:38 death (old binary

## TreeSitter warning flood on exit (fixed via opentui patch)

Symptom (2026-09-19, old pre-sync binary): exiting a code-heavy session view
dumps dozens of `Code highlighting failed, falling back to plain text: warn:
TreeSitter client destroyed` blocks with full stacks into the shell scrollback,
interleaved with the next prompt.

Mechanism: key-triggered exit → renderer destroy → `finalizeDestroy` →
`destroyTreeSitterClient` → `rejectPendingRequests(new Error("TreeSitter client
destroyed"))`. Every still-queued syntax-highlight request (one per visible
code block) rejects; `CodeRenderable`'s catch logged `console.warn` **before**
checking `this.isDestroyed`, so each rejection printed the stored destroy stack
via the external-output passthrough.

Forensics: the stack's chunk hashes (`chunk-2vn5v3v7`, `chunk-tx410jhg`,
`chunk-x0hfdhs6`) exist only in the old build — not in `0.0.0-main-202609190133`
or later. Not reproducible on new builds via tmux (ready-exit, mid-replay
SIGTERM, 1MB session clone all exit clean), but the unguarded log path is
version-independent, so the fix is kept as a belt-and-braces guard.

Fix: in `patches/@opentui%2Fcore@0.5.17.patch`, the catch in `CodeRenderable`
(`chunk-bun-h3ggawd9.js` / `chunk-node-kc1sqq2a.js`) checks `this.isDestroyed`
**before** `console.warn` — teardown-time highlight failures are silent.
Verify after install: `grep -c "Math.max(16, targetFrameTime"` and the
isDestroyed-before-warn order in both chunk files under
`packages/tui/node_modules/@opentui/core/`.

Note: patch hunks are line-numbered against the pristine package. The
highlight-guard hunk must come **before** the rerender-floor hunks per file
(ascending line order); all hunks are net-zero line changes, so they never
shift each other's line numbers.
